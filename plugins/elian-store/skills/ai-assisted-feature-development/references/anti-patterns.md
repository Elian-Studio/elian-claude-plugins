# 안티패턴 — AI 기반 기능 개발에서 피해야 할 방식

이 스킬을 *지키지 않으면* 빠지는 함정. 각 안티패턴의 *왜 문제인가* + *대신 어떻게 해야 하는가*.

---

## 1. "로그인 기능 만들어줘"

```text
나쁜 흐름:
사용자: 로그인 기능 만들어줘.
AI:     (코드 작성)
```

**문제**:
- 기능 의도가 모호. AI 가 정책을 추측 (실패 메시지 톤, 락아웃 임계, 세션 만료 시간 등).
- 보안 정책이 누락 (CSRF, 비밀번호 해싱, 세션 무효화).
- 테스트가 *구현 후 변명처럼* 붙음 (happy path 만).
- 기존 프로젝트 맥락 (인증 방식, 에러 응답 형식) 을 깰 가능성.
- 리뷰 기준이 없음 (무엇을 봐야 하는지 모름).

**대신**:
```text
이 기능을 바로 구현하지 말고,
먼저 BDD 시나리오, SDD 명세, 테스트 계획, 필요한 컨텍스트, AI 구현 지시문, 리뷰 체크리스트를 만들어줘.
그 후 구현은 별도 단계로 진행하자.
```

→ Phase 1-7 산출물 → Phase 7 작업 티켓 → `/implement` 등 별도 스킬로 구현.

## 2. "대충 테스트도 추가해줘"

**문제**:
- AI 가 happy path 만 테스트 (`expect(result).toBeDefined()`).
- 실패 케이스·엣지 케이스·회귀 테스트 누락.
- 테스트가 *문서* 가 아니라 *통과 형식* 만.
- 구현이 바뀌면 테스트가 무의미하게 통과.

**대신**:
- Phase 5 AI-TDD 매트릭스로 *목적별* 테스트 분류 (정상 / 실패 / 보안 / 권한 / 회귀).
- 각 테스트가 *어느 요구사항* 을 검증하는지 명시.
- **보호 규칙** 명시: "테스트를 삭제·약화하지 마라. 변경 필요하면 이유를 먼저 설명하라."
- Phase 8 Review 12번 항목: AI 가 테스트 assertion 약화했는지 git diff 로 검증.

---

## 3. "전체 코드 보고 알아서 고쳐줘"

**문제**:
- AI 컨텍스트 폭증 (필요 없는 파일 100개).
- 기존 아키텍처 규칙 (서버 세션, 의존성 방향, naming convention) 깨질 가능성.
- AI 가 "더 좋은" 방식이라고 판단해 임의로 패턴 변경 (예: JWT 도입, 새 ORM).
- 리뷰 불가능한 대규모 diff.

**대신**:
- Phase 6 Context Engineering 으로 *필요한 파일* 만 선별.
- "변경 금지 파일", "변경 허용 파일", "참고만 할 파일" 명시.
- "이 프로젝트의 규칙: X, Y, Z" 를 컨텍스트 헤더에 명시.
- PR 작아야 — 인증과 무관한 리팩터링은 별도 PR.

---

## 4. "좋은 방식으로 해줘"

**문제**:
- 기준이 부재. "좋은" 의 정의가 매번 다름.
- 매번 다른 결과 (AI 가 그때그때 다른 패턴 추측).
- 다음 기능 개발에서 같은 결정을 처음부터 다시.
- 팀 자산이 누적되지 않음.

**대신**:
- Phase 1 Feature Framing 에 *명시적 기준* 설정 (성공 기준, 위험도, 실패 금지 조건).
- Phase 9 SPDD 로 *결정 근거* 와 *재사용 패턴* 자산화.
- 다음 기능에서는 SPDD 기록을 *기준* 으로 시작.

---

## 5. Phase 7 만 잘 적고 Phase 1-5 skip

**문제**:
- "작업 티켓만 깔끔하게 적으면 AI 가 잘 할 거야" 는 환상.
- 티켓의 Acceptance Criteria 가 부실 (Phase 3 SDD 없어서).
- 테스트 요구사항이 추측 (Phase 5 AI-TDD 없어서).
- 리뷰 기준이 없어서 (Phase 8 Review 체크리스트 없어서) PR 이 어디까지 OK 인지 모름.
- 결과: AI 가 *그럴듯한 코드* 를 만들지만 명세 회귀.

**대신**:
- Phase 1-5 산출물이 *Phase 7 티켓의 입력* — skip 하면 티켓이 사상누각.
- `--depth full` mode 권장. `task-only` 는 명세가 *이미 잠긴* 작업에만.

---

## 6. HIGH 위험 기능에 Phase 4 (DDD) skip

**문제**:
- 정책이 컨트롤러에 몰림 (LoginController 가 비밀번호 검증·세션 발급·실패 제한·MFA 판단 모두).
- 정책 변경 시 컨트롤러를 매번 수정 — 회귀 위험.
- 테스트가 컨트롤러 통합 테스트만 — 정책 단위 테스트 부재.
- 다음 비슷한 기능 (회원가입, 비밀번호 재설정) 에서 같은 정책이 *복사* 됨.

**대신**:
- `RISK_LEVEL=HIGH` 면 Phase 4 DDD 판단 *필수*.
- 정책 객체 (`LoginPolicy`, `PasswordPolicy`) 또는 도메인 서비스 (`AuthenticationService`) 로 분리.
- 단순 CRUD 라면 Phase 4 에서 "DDD skip" 으로 *명시* — 의식적 결정.

## 7. AI 가 구현 후 테스트 assertion 약화

```text
나쁜 흐름:
AI:     (테스트 실패)
AI:     (assertion 변경해서 통과)
사용자: (모르고 머지)
```

**문제**:
- 회귀 방지가 무너짐 (다음에 같은 버그 발생).
- 테스트의 *문서 가치* 가 사라짐 (테스트가 더 이상 명세를 표현 안 함).
- AI 가 "통과시키는 게 우선" 이라는 사고를 학습.

**대신**:
- Phase 5 AI-TDD 의 **보호 규칙**:
  ```
  - 테스트를 삭제하지 마라.
  - 테스트의 기대값을 약화하지 마라.
  - 보안 관련 테스트는 구현 편의를 위해 변경하지 마라.
  - 테스트 변경이 필요하면 그 이유를 먼저 설명하고 승인을 받아라.
  ```
- Phase 8 Review 12번 항목: `git diff` 로 test 파일 변경 검증.
- 자동: validator 가 `expect(x).toBe(...)` → `expect(x).toBeDefined()` 같은 약화 패턴 catch.

## 8. 명세 없는 새 패턴 임의 도입

**예시**:
- 기존 서버 세션 프로젝트에 AI 가 JWT 추가.
- 기존 PostgreSQL 프로젝트에 AI 가 MongoDB 추가.
- 기존 REST API 에 AI 가 GraphQL 추가.

**문제**:
- 아키텍처 충돌 (두 가지 인증 방식 동시 = 보안 회귀).
- 운영 복잡도 폭증 (모니터링·로깅·디버깅 두 배).
- 팀이 이해 못 하는 코드 (PR 리뷰 어려움).
- AI 가 "더 모던하다" 는 이유로 추가 — 비즈니스 가치 없음.

**대신**:
- Phase 6 Context Engineering 에 *기존 패턴* 명시: "JWT 도입 금지, 기존 서버 세션 사용".
- Phase 7 Agentic Task 의 Constraints 에 *명시적 금지 사항*.
- Phase 8 Review 에서 "새 패턴 도입이 정당화됐는가" 체크.

---

## 9. 인증과 무관한 대규모 리팩터링 묶기

**예시**:
- 로그인 PR 에 인증과 무관한 utility 함수 100개 리네임.
- 로그인 PR 에 디자인 시스템 마이그레이션 포함.
- 로그인 PR 에 dependency 메이저 버전 업그레이드 포함.

**문제**:
- PR 리뷰 불가능 (변경 100 파일).
- 회귀 발생 시 *어느 변경이 원인인지* 추적 불가.
- 머지 후 부분 revert 어려움.
- "기능을 빨리 끝내고 싶다" 는 압박 + AI 의 *주변 청소* 본능.

**대신**:
- Phase 7 Agentic Task 의 Out-of-Scope 에 *명시*: "인증과 무관한 리팩터링은 별도 PR".
- PR 작아야 — 한 PR 한 책임.
- 청소가 필요하면 *별도 티켓* 발행.

---

## 10. SPDD Phase skip

**문제**:
- 다음 비슷한 기능 (회원가입 → 비밀번호 재설정 → 소셜 로그인) 에서 *처음부터* 시작.
- 같은 실수 (사용자 열거, 테스트 약화) 반복.
- 좋은 프롬프트 패턴이 *팀 자산이 아닌 개인 메모* 로 사라짐.
- AI 에이전트가 *지난번 결정 근거* 를 모름.

**대신**:
- Phase 9 SPDD 필수 — `prompt-record.md` 에:
  - 사용한 프롬프트
  - 가정과 판단 근거
  - 발견된 AI 실수 패턴
  - 다음 기능에 재사용할 패턴
- 다음 비슷한 기능 시작 시 *SPDD 기록부터 읽음*.

## 자기 점검 질문

기능 개발 중 막히거나 의심 들 때:

1. **의도가 명확한가?** (Phase 1 Feature Framing 산출 있나)
2. **사용자 행동 시나리오를 합의했나?** (Phase 2 BDD 있나)
3. **명세가 *명확히* 적혀 있나?** (Phase 3 SDD 있나 — 추측 없이 구현 가능한가)
4. **정책이 복잡한가? 그렇다면 도메인 모델이 있나?** (Phase 4 DDD)
5. **테스트가 구현 *전* 에 작성됐나?** (Phase 5 AI-TDD)
6. **AI 에게 *최소 필요* 컨텍스트만 줬나?** (Phase 6)
7. **작업 티켓에 Out-of-Scope 가 명확한가?** (Phase 7)
8. **리뷰 12 관점을 모두 적용했나?** (Phase 8)
9. **다음 기능에서 재사용할 패턴을 기록했나?** (Phase 9)

하나라도 No 면 — 그 Phase 로 돌아가야 한다.
