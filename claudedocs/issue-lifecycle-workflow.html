📌

issue-open is the single intake entry point for feature work, existing-feature changes, and bug fixes. A separate intake-spec step does not appear in the intended workflow.

Workflow at a glance

↳

The decisive split is behavioral: a new capability routes to implement, an intentional change to working behavior routes to improve, and behavior that violates its contract routes to fix.

Planning readiness

Planning is insufficient
Clarify inside issue-open
  1. Identify the largest missing fact.
  2. Ask one question at a time.
  3. Capture problem, scope, constraints, exclusions, and acceptance criteria.
  4. Use brainstorm only when competing solution options need a decision.
  5. Return to the readiness check.
Planning is already firm
Route immediately
  1. Compare the issue statement with current code.
  2. Confirm the understood scope in a short summary.
  3. Do not repeat the interview.
  4. Do not rewrite the same plan into duplicate documents.
  5. Classify and route the work.
📝

Missing facts stay within issue-open. brainstorm is optional and handles solution choice, not routine requirements capture.

Work-type routing

Work typeDetection ruleDesign gateExecution workflow
New capabilityThe system gains behavior that did not exist beforeUse design-feature for DB, API, UI-flow, cross-module, or cross-service decisionsimplement
Existing feature changeCurrent behavior works, but the target behavior intentionally changesUse design only when the change alters contracts or architectureimprove
Existing surface with a new capabilityThe request is attached to an existing screen or service but expands the product contractTreat as new development, not a cosmetic improvementdesign-feature when needed, then implement
Bug fixActual behavior violates the intended or documented behaviorNo design step unless the fix changes the contractfix

Scenario 1 — insufficient planning

Example issue: “Improve the appointment screen”
The issue does not identify the affected user, the failing journey, the target behavior, exclusions, or a testable completion condition.
1
issue-open detects the gaps
The issue cannot be routed safely yet.
2
Clarify one decision at a time
Start with the question that most changes scope: “Which user journey is currently failing?”
3
Capture the boundary
Record the chosen behavior, exclusions, constraints, and acceptance criteria in the issue context.
4
Route only after readiness
If this changes working behavior, continue with improve. If it introduces a new capability, continue with implement.

Scenario 2 — firm planning

Example issue: precise behavior and acceptance criteria
The issue already defines the affected user, current behavior, target behavior, out-of-scope items, API or UI constraints, and testable acceptance criteria.
1
issue-open validates the issue against the repository
It checks that named components and assumptions exist.
2
Confirm once
Return a short scope summary instead of starting another requirements interview.
3
Route directly
Choose implement, improve, or fix from the requested behavioral change.

Scenario 3 — new development

Small and clear
issue-open
→ planning ready
→ new capability
→ implement
→ verify and review
→ issue-close
Design decisions required
issue-open
→ planning ready
→ new capability
→ design-feature
→ implement
→ verify and review
→ issue-close

design-feature is conditional. It is justified when the issue changes database shape, public contracts, user journeys, module boundaries, infrastructure, or multiple services.

Scenario 4 — existing feature change

Intentional behavior change
The current feature works as designed, but the desired behavior changes.

Route to improve
New capability on an existing screen
Existing location does not make the request an improvement. A new product capability remains new development.

Route to implement

The improve workflow captures the current behavior, defines the target behavior, protects existing tests, adds new expectations, and compares before and after.

Scenario 5 — bug fix

1
issue-open confirms the contract
Record expected behavior, actual behavior, and a reproducible condition.
2
fix identifies the root cause
Do not patch only the visible symptom.
3
Prove Red → Green
Add a regression test that fails before the fix and passes after it.
4
Verify the blast radius
Run relevant integration checks and review sibling sites with the same root pattern.
5
Close with evidence
issue-close records the root cause, regression test, verification, and remaining monitoring.

Ownership summary

SkillOwnsDoes not own

brainstormComparing viable solution options and locking a decisionRoutine requirements capture
design-featureNecessary architectural and contract decisionsEvery new feature by default
implementNew capability developmentRepairing broken existing behavior
improveIntentional changes to working behaviorNew capabilities disguised as improvements
fixRoot-cause repair and regression protectionProduct-policy changes
issue-closeFinal decisions, changes, proof, trade-offs, remaining work, completion stateRequirements intake

⚠️

This document describes the intended lifecycle. The current repository still presents intake-spec as a separate requirements front door and explicitly excludes requirements gathering from issue-open. Those skill and README contracts must be revised before the implementation matches this workflow.
